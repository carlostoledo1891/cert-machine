δ₃ in HOL4: the checker and its blind benchmark, live

δ₃ = 117/2192 (Erdős #1186) rests on five exact certificates. A checker for them is written in HOL4 and runs in HOL4’s kernel; the proof that the checker is sound is being built. Its lemmas are a blind benchmark: Claude Opus 5.5 and GPT-6.2 Astra attempt the same 162 statements, some false on purpose, and the HOL4 kernel judges every attempt.

A live page, rebuilt from its records as the run moves; this build reads them up to 15:10 UTC on 25 November 2026. The run has ended. The certificates, and the exact verifier that decided them, are on the δ₃ report. Nothing here is refereed; the change log is at the foot.

what went wrong, first

What went wrong during the run, and what was done

Said first, in plain words, as the records state it. Each was found and acted on while the run was open, before the answer key is opened.

  1. 13:41 UTC The judge’s log could be read across the two families.

    The judge writes every attempt of both families to one log. The brief forbade reading the other family’s folder, but not that log. A Claude agent read it; the GPT family was ahead, so a Claude agent reading the log could see GPT outcomes before attempting the same statement.

    Done. At 13:42 UTC the 4 Claude agents then running were told not to read the log or other agents’ results, and to report whether they had, and for which statements. Each later Claude agent gets the same message at its start.

    In the scoring. The blinding audit counts every read of the log, per agent and per statement. The Claude family is scored twice: with all its statements, and without the statements an agent could have seen in the log first.

  2. 13:51 UTC Work from before the run, by an agent that had seen the answer texts, could be read.

    A folder the proving agents were allowed to read still held earlier attempts and proofs written before the run by a Claude agent that built the harness and had read the texts of the true statements. One Claude proving agent used that material for 2 of its statements. Also readable: the first answer key’s statement list, whose lists identify 41 of its 44 planted texts (this run uses the same texts, renumbered), and one accepted proof from before the run.

    Done. At 13:51 UTC all of it (11 folders, the first statement list and the accepted proof) was moved out of the folders the agents may read; a note stands in its place.

    In the scoring. Those 2 statements are marked contaminated for the Claude family, which is reported with and without them. The blinding audit lists every read of the moved material by any agent of either family, with its time; any statement decided after such a read is reported separately.

  3. 13:29 UTC A correct refutation would have stopped the run.

    A refutation proves that a statement’s text, taken alone without its “may use” hypotheses, is false. A decoy whose text is a planted (false) text is true as a whole, because one of its hypotheses is false, yet its text can be refuted. The protocol said that refuting a decoy meant a kernel or judge fault and stopped the run. This was found during the run and written down before the answer key is opened.

    Done. Ruled at 13:29 UTC, before the key is opened: such a refutation is correct. It is reported in its own column, “text refuted”, beside “proved”, and it does not stop the run. A family that refuted such a decoy first can no longer prove it, and the report says so.

    In the scoring. The rule that stops the run stays for a refutation of a true original or of a decoy whose text is true.

  4. 13:47 UTC A planted statement can be true, vacuously.

    A Claude agent found that a planted statement’s “may use” list can name a decoy whose text is false. The planted statement then holds vacuously and has a correct kernel proof, and the gate “zero planted statements proved” would have flagged a correct proof as a fault.

    Done. Ruled at 13:47 UTC, before the key is opened: the gate judges what the kernel judged. Zero “proved” on a statement whose goal is false, and zero “refuted” on a statement whose text is true; either one would mean a kernel or judge fault. A planted statement whose goal holds vacuously is scored in its own class.

    In the scoring. Every statement is classed by the truth of what the kernel was asked to judge, read from the key once it is opened.

The rulings made during the run

  • 13:29 UTC. A refuted decoy text counts as correct, in its own column; it does not stop the run.
  • 13:47 UTC. Agents, not people, read the accepted scripts: one Claude and one GPT-6.2 reader, each alone, every script. The report will say that no person read them.
  • 13:47 UTC. The gate judges what the kernel judged: no proof of a false goal, no refutation of a true text.

Known limits, said before the results

  • The first answer key, frozen at 22:03 UTC on 24 November, was printed into AI session transcripts on the machine that runs the benchmark. It was replaced before the run by a fresh key, frozen at 10:25 UTC on 25 November and encrypted under a passphrase that one person, Carlos Toledo, holds.
  • The Claude agents that built the harness read the texts of the true statements. The proving agents are other agents; the blinding audit checks what each of them read.
  • Nothing stops an agent from reading a file: the machine does not restrict reads. The blinding rule is checked afterwards, on every agent’s tool log.
  • Agents of the same family may read each other’s scripts. The brief allows it; reuse is reported, not excluded.
  • The decoys remove the signal that used to mark the true statements; weaker signals remain, were measured before the run, and are reported with the results.
  • The judge trusts the files HOL4 writes. A deliberate forgery from inside a build would be stopped only by a text filter on the script and by reading the script, which is why every accepted proof is rebuilt and read (below).
  • The judge kept running through the pause: 1 Claude Opus 5.5 attempt and 2 GPT-6.2 Astra attempts, already submitted when the agents stopped (11:39 UTC), were judged during it.

how it works

The benchmark

  • Two model families. Claude Opus 5.5 (claude-opus-5-5), one agent per batch, and GPT-6.2 Astra (gpt-6.2-astra, through the Codex command line), one session per batch.
  • The same statements, the same order. Both families get the same 162 statements about the checker, in the same nine batches of 18, with the same brief and no hints beyond it. Each statement either holds, or is false on purpose (planted), or is a decoy; the agents are told some are false.
  • At most 3 attempts per statement. Proofs and refutations together, per family. A family stops at its first judged outcome on a statement: proved, or refuted (the statement shown false).
  • One judge, the same limits. Every attempt is a complete HOL4 script, built on a rented judge machine with no network, under the same limits for both families: 600 s of wall time, 1,200 s of CPU per process, 6 GB of memory. The kernel’s answer is the outcome: proved, refuted, failed, timeout or refused. HOL4 is pinned at trindemossen-2-v10, Poly/ML at v5.9.2. Every attempt of the run so far was judged on that one machine, by one version of the judge, against one frozen statement list.
  • A sealed answer key. Which statements are true, planted or decoys is in a key encrypted before the run (frozen 10:25 UTC on 25 November 2026) under a passphrase that one person, Carlos Toledo, holds. Nobody knows which statements are which until it is opened, after the run.
  • What an agent may not do. Run HOL4 itself (every build goes through the judge), or read the true statements’ texts, the other family’s folder, or any agent’s session transcript. Every agent’s tool log is audited for this after the run.
  • Controls first. 9 of 9 controls, the memory limit and both refutation controls passed on the judge machine before the run.
the work

The checker: what is proved, and what is not

The checker is a set of HOL4 functions over integers and lists. Given a certificate, it rebuilds the polynomial identity, forms the integer matrix and tests it, and returns T or F. It is written in HOL4 so that two things become possible: running the certificates inside HOL4’s kernel, and proving there that a T means the bound holds.

Proved

  • The checker runs in the kernel. For each of the five certificates, HOL4 proves ⊢ check <data> ⇔ T: the four slabs in 1.15–1.36 s each, the inner certificate (22,808 forms) in 1.29 s. The same check in JavaScript takes 0.18 s on the same machine: the kernel is 6.4 times slower. A cover check proves the five regions reach from 0 to 1/2 with no gap. Each theorem carries only HOL4’s disk tag, with no axioms and no hypotheses.
  • Forgeries are refused. Of the 40 planted forgeries of the existing battery, 36 give F in the kernel, the 3 cover forgeries give F, and the loader refuses the malformed one before the kernel; 6 more forgeries give F too.
  • The dominance lemma. Weighted diagonal dominance implies positive semidefiniteness (and, strictly, definiteness), proved in HOL4. A search of HOL4’s sources at the pinned release found no theorem on semidefiniteness or diagonal dominance.
  • A compiled copy. The same checker, compiled by CakeML into a binary, agrees with the kernel on 52 of 52 inputs, at 0.28–0.32 s per certificate. Kernel runs at two HOL4 releases (-v9 and -v10) give byte-identical theorems on all 51 inputs that reach the kernel.

Not proved

  • Soundness, not yet. A kernel theorem above says the checker returns true on the data. It does not yet say the bound holds. The next theorem is that an accepting slab check implies the bound on its region; the same for the inner and cover checks comes after. The benchmark’s statements are the lemmas of that proof.
  • The model constants are data. The areas and constants of the extremal colouring are computed by the JavaScript verifier and loaded into HOL4 as data, not derived in it.
  • The analytic reduction is not in HOL4. The step from the five inequalities to δ₃ = 117/2192, and the uniqueness of the extremal colouring, are not in HOL4.
  • The witness is untrusted. The Gram factor, the weights and the scale are hints written in floating point. A wrong hint can only turn T into F, so F on a forgery says the check fails with that witness, not that no witness exists.
  • Strictness is tested by strict diagonal dominance, which is sufficient for positive definiteness but not necessary; the JavaScript verifier tests leading minors, which is exact. Both accept all five certificates.
  • The trusted base. HOL4’s kernel, including its compute primitive. That primitive is a port of the compute facility proved sound for Candle (O. Abrahamsson, M. O. Myreen, M. Norrish, H. Kanabar, J. Åman Pohjola, J. Automated Reasoning 69(1):7, 2025); the port itself is not proved inside HOL4. The binary adds CakeML’s released compiler binary, the C stubs of its basis library and the link step.

Related work

The full statement δ₃ = 117/2192 is formalised in Lean by Snively (erdos-1186, v1.0.0, 26 October 2026). Star Fleet Math stated the value, with an exact rational sum-of-squares certificate, by 15 July 2026 (Internet Archive capture 20260715002525). This work is a checker in HOL4 for the certificates; it does not state δ₃ as a HOL4 theorem.

what happens next

What happens next, in order

  1. 1The run ends. When every statement is judged or at the cap for both families, or the run is stopped. The judge machine is stopped, its log brought home, and the machine deleted.
  2. 2A fresh rebuild of every accepted proof. Each accepted script is built again, alone, in a new process against the frozen statements; an attempt counts only if the rebuild gives the same decision.
  3. 3Two readers for every accepted script. One Claude and one GPT-6.2 agent, each alone, read every accepted script against a seven-item checklist. No person reads them, and the report will say so.
  4. 4The blinding audit. Every agent’s tool log is read for forbidden reads: the judge’s log, the moved material, the answer texts.
  5. 5The key is unlocked. Carlos Toledo types the passphrase; the key says which statements are true, planted or decoys. Nobody knows that before.
  6. 6Scoring. By what the kernel judged, per family and per class, with exact 95% intervals, the Claude family also without the statements touched by the two leaks above.
  7. 7A non-blind builder finishes the slab lemmas. Any lemma of the slab proof left unproved after the run is finished by a builder agent that is not blind. Those lemmas are labelled non-blind, and the scores count only blind attempts.
  8. 8The slab theorem. The theorem that an accepting slab check implies the bound on its region, for the four slabs: the next milestone of the soundness proof.
  9. 9A public repository. The checker, its proofs and the run’s records in a small public repository of their own.
