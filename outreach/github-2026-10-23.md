## 4. HELD — the unknown-config-key issue (comparator → `lake check`)

Found in the cryptids kernel lane (commit 3f562b2a): comparator's `Config` derives `Lean.FromJson`, which ignores unknown
keys, so `"nanoda": true` (the first dispatch, run 39887837955) ran Lean's kernel alone and still printed "Your solution is
okay!" with exit 0; `enable_nanoda` (run 39889985974) ran both. leanprover/comparator is ARCHIVED (merged into Lean core as
`lake comparator` / `lake check` in v4.35.0); the same `Config … deriving Lean.FromJson` and `Lean.fromJson? (α := Config)`
are in leanprover/lean4 src/lake/Lake/CLI/Check.lean. NOT POSTED: an issue on leanprover/lean4 should carry a reproduction
under `lake check` itself (a hosted-runner run with Lean ≥ v4.35.0 and a misspelled key), which we have not run. The draft,
for when it is:

~~~~markdown
`Config` in `Main.lean` derives `Lean.FromJson`, and the derived instance ignores fields it does not know. So a config with a wrong or misspelled key — `"nanoda": true`, `"enable_nanod": true`, `"external_kernel": {…}` — parses, comparator runs with Lean's kernel only, and the run ends "Your solution is okay!" with exit code 0. The log does name the kernels that answered ("Lean default kernel accepts the solution" and no nanoda line), but a CI step that checks only the exit code cannot tell a two-kernel audit from a one-kernel one.

We hit this ourselves (at comparator `ca04cfc7`; `Main.lean` is unchanged at `865edc14`): auditing google-deepmind/cryptids with the repository's own `comparator/constructive.json` and `comparator/all.json`, we added `"nanoda": true`. Both configurations passed, under Lean's kernel alone ([run](https://github.com/carlostoledo1891/cert-machine/actions/runs/39887837955)); with `"enable_nanoda": true` both passed under both kernels ([run](https://github.com/carlostoledo1891/cert-machine/actions/runs/39889985974)). We only noticed because our recorder reads the kernel lines rather than the exit code.

A small fail-closed fix: before `fromJson?`, check the top-level keys of the parsed object against the known field names and refuse with an error naming any unknown key. Printing the active kernel list at start would also help.
~~~~
