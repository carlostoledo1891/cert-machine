**Why `MainResults` is its own challenge module.** Lean shares auxiliary proof terms within a
module. The first Comparator run used a single challenge file and was rejected with
`Const does not match between challenge and target 'MainResults.InTime'`: in that file,
`InTime` reused the `(2 : ℝ)` side proof `OAI.ParityWL.Complexity.PositiveRateETH._proof_1`
created a few lines earlier, while in the solution `MainResults` is a separate module with its own
`MainResults.InTime._proof_1`. Keeping Anthropic's file whole, as its own module, reproduces the
solution's module boundary. A `pp.all` comparison confirmed that the ParityLifts slices already
elaborate identically in one module (their auxiliary proofs keep their own names).

The bridge and challenge build outputs were deleted before the Comparator runs, so Comparator built

**Qualifications of the harness run** (all three are environment limits; the VPS run removes them):

1. The harness kernel offers Landlock ABI v7. Current `landrun` main requires ABI v10 and the
   release contemporary with this Comparator (`811cfff`) requires v9; both refuse to start here.
   `3ee150a`, the last commit before the ABI-9 requirement, enforces the sandbox here (a read
   outside the allowed paths is denied) with the ABI-7 feature set.
2. The `systemd-run --property=RestrictAddressFamilies=~AF_UNIX --user` wrapper recommended by
   Comparator's README is unavailable in the harness (no user systemd bus).
3. nanoda inside Comparator aborted with a thread stack overflow (Comparator's generated nanoda
   configuration uses nanoda's default 32 MB worker stack, and passes no environment variables).
   This is a resource abort, not a type-checking verdict; the Comparator configuration therefore
   keeps `enable_nanoda: false`, matching the repository's other challenges, and nanoda is run
   separately below.
